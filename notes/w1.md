# W1: Go as a first-class toolchain, round-1 friction fixes, self-hosting

Date: 2026-10-15. Local VM `altwasm` (2 vCPU / 3.8 GB, noisy: the same
cold step varied 2-4x between runs). Go go1.27.2, wasmtime 49.0.3.

## What changed

**Merge.** `e5-spawn` merged into main without conflicts. E5 had branched
after E4, so the clang driver, wasip2 components and `wasmdev_proc` coexist.
`scripts/build-go-toolchain.sh` now also builds `gofmt`, which `go fmt` needs.

**Go tool** (`scripts/register-go.sh`, all through `PUT /v1/tools/go`).
The tool is the E5 toolchain as a tar: tool.json plus the pristine GOROOT
and the wasip1 binaries. New tool-manifest fields are generic data that the
control plane interprets:

| field | Go uses it for |
|---|---|
| `spawn: true` | `cmd/go` gets `wasmdev_proc` and spawns compile/link/vet/test binaries. User programs don't get it. |
| `shared: [{name: gocache, guest: /gocache}]` | GOCACHE in `/data/cache/go/gocache`, read-write, shared by every workspace |
| `scratch: /tmp`, `scratch_compiler: winch` | GOTMPDIR is per invocation. Test binaries spawned from it are compiled with Winch and kept in memory only. |
| `env` with `{cpus}` | `GOFLAGS=-p={cpus}`, where cpus is the host core count (`WASMDEV_HOST_CPUS`). Also GOPROXY=off, GOTOOLCHAIN=local, CGO_ENABLED=0, GOSUMDB=off, HOME/GOPATH in scratch. User `env` now overrides tool env. |
| `precompile_modules` | Cranelift-compiles gofmt, compile, link, asm, vet, buildid, cover, test2json and pack at registration, not only `go` |
| `warm: {files, cmd}` | Runs once after precompile in a scratch workspace through the normal job path: build, vet and test a program that imports net/http, encoding/json and testing. That fills GOCACHE with the std library. A marker in the shared dir prevents re-running at every startup. Tool status: `running → warming → done`. |

`{"cmd": "go test ./..."}`, `go build -o app.wasm .`, `go vet` and
`go run` all work. Built programs run as `./app.wasm` or as services. Go
services use the `WASMDEV_LISTEN_FD` snippet from GET / (see
`examples/go-w1/srv`).

**Host** (`host/src/rt.rs` is new; exec/cache/proc changed):
- **One engine per (compiler, max_wasm_stack).** wasmtime reads both
  settings engine-wide. Engines are created lazily, each with its own
  p1/p2 linkers, and the epoch thread ticks all of them.
- **Stack limits.** The default `max_wasm_stack` is now 8 MiB (wasmtime's
  default is 512 KiB). Specs can request up to 256 MiB, and children
  inherit the parent's limit.
- **Disk cache sharing.** Cranelift engines that differ only in stack size
  share the disk cache; the compat hash is unchanged, so the old `.cwasm`
  files still load.
- **Winch.** Available as `compiler: winch`. It falls back to Cranelift if
  Winch rejects a module. It is used for:
  - modules spawned from a mount marked `compiler: winch`;
  - the `tier_up` mode. That mode uses Cranelift code if it is already in
    memory. Otherwise it runs the Winch code and then compiles Cranelift in
    a background thread (one at a time) for the next run.
- **Ephemeral cache entries.** Workspace programs and test binaries are
  cached in memory only, at most 32. They no longer fill the disk cache,
  which fixes E5 problem 6 for these modules.
- **Compile locks by size.** Modules under 16 MB use their own compile
  lock. A user program used to wait 70-87 s behind the Go tools' Cranelift
  compile.
- **Trap codes.** The status carries `trap` (wasmtime's trap code in
  snake_case) and the `compiler` actually used.
- **`exec_ready(handle)` import.** wasip1 services are ready when the guest
  has called `sock_accept` (a small vendored-patch flag). wasip2 services
  are ready when a TCP connect to the port succeeds.
- **Spawn is opt-in** (`spawn: true`).

**Control plane:**
- **cmd mini-shell** (`sh.go`, `shrun.go`):
  - `&& || ;`
  - `|` (buffered: stages run one after another through temp files)
  - `< > >> 2> 2>> 2>&1`, relative to the workspace
  - builtins `echo cat cmp diff true false`

  Exit status follows sh. An unknown command gives 127; it is still a 400
  when the line is only `&&` chains, so typos fail fast. Test runners can
  now run inside the service:
  `./prog < in.txt > out.txt && diff out.txt want.txt`.
- **Per-run options.** `max_wasm_stack` applies to workspace programs and
  to what spawning tools run. `compiler` is `tiered` (default), `cranelift`
  or `winch`.
- **Trap explanations** (`explainFailure`):
  - `stack_overflow`: names the limit and how to raise it;
  - an out-of-bounds fault at an address of 0xff000000 or higher: reported
    as a C linear-stack overflow, with the `-Wl,-z,stack-size` hint;
  - `unreachable`, division by zero, bad indirect call, and
    `long_double_not_supported` (suggests `-lc-printscan-long-double`);
  - the raw error is kept, and so is stdout written before the trap.
- **cc/c++ stack size.** Links get `-Wl,-z,stack-size=1048576` unless the
  user sets a stack size. This is data in the llvm tool.json
  (`clang.default_stack_size`).
- **Services.**
  - `url` is `https://<public-host>:<port>/` when a public host is
    configured (scheme from `WASMDEV_PUBLIC_SCHEME`); `local_url` is
    `http://127.0.0.1:<port>/`.
  - `wait_ready: true` (with `ready_timeout_ms`, default 30 s) returns
    `ready`/`ready_ms`. If the service exits or times out, the response
    includes `ready: false` plus stdout/stderr tails.
  - `ready_ms` is recorded for every service.
- **GET /** adds sections on the shell, limits, compilers, WASI libc
  gotchas (tmpfile, long double, threads, processes, emulation flags,
  stack, stdout buffering on traps) and Go, including a service snippet.
- **Unit tests** cover the shell parser (words, quoting, globs, operators,
  fd-2 rules, errors), line diff, trap explanations, the stack-size
  detection and the `clang -###` parser.

## Measurements

### Winch vs Cranelift (Go programs, compile = first `load_ms`)

| module | Cranelift compile | Winch compile | ratio |
|---|---|---|---|
| app.wasm (2.6 MB, fmt + 2 pkgs) | 2.16 s | 0.45 s | 4.8x |
| srv.wasm (11.5 MB, net/http) | 9.3 s | 1.7 s | 5.4x |

Runtime of a CPU-bound program (sha256 of 32 MB plus sort and map,
warm): Cranelift 0.93 s, Winch 1.9 s. So Winch code is about 2x slower.

The policy follows from this. Test binaries run once, so they use Winch.
Workspace programs and services use tiered compilation. With tiered, the
first run of cpu.wasm took 2.6 s (Winch) and the second 0.7 s (Cranelift
from the background compile). A service's first `wait_ready` went from
10.4 s (Cranelift) to 1.0-2.3 s.

### Self-hosting (`scripts/selfhost.sh`)

All of this goes through the API on the native-built control plane:
- `go vet ./...` on control/: 0.7 s.
- `go test -v -count=1 ./...`: 3.7 s. All 7 tests pass. The test binary is
  a wasm child of wasm `go`.
- `go build -trimpath -buildvcs=false -o control.wasm .`: 104 s the first
  time (std packages beyond the warm-up set, such as archive/tar, regexp
  and crypto, compiled once into the shared GOCACHE); later builds take a
  few seconds.
- **The service-built control.wasm is byte-identical to the native build**
  (sha256 `d4bf0455…`, 12.3 MB). Both use go1.27.2 with the same flags
  (GOOS=wasip1 GOARCH=wasm CGO_ENABLED=0 -trimpath -buildvcs=false); GOFLAGS
  -p does not affect output.
- The host was restarted with the service-built control.wasm. The API was
  up in 40 ms (the identical bytes hit the disk cache). C build + run
  worked. The self-built control plane then ran its own tests and rebuilt
  itself to the same bytes, a fixed point.
- `scripts/serve.sh` now always builds control.wasm with these flags. The
  live service runs this build, with go, llvm and wasm-tools registered.

## Problems found

1. **The compile lock starved small modules.** A 100 KB C program waited
   70-87 s behind `compile.wasm`'s Cranelift compile during Go
   registration. Fixed with a separate lock for modules under 16 MB.
2. **The background tier-up competed with the foreground Winch compile.** A
   service's first ready time went 1.7 s → 5.6 s. Fixed by starting the
   background compile after the Winch load.
3. **Go keeps reachable wasm imports.** The control plane's own test binary
   failed to instantiate (`unknown import wasmdev::exec_start`). A
   package-level `drivers` map initializer made the clang driver, and
   through it the host imports, reachable in every binary of the package.
   It is now a `driver()` switch, and the test binary has no wasmdev
   imports. The general lesson: keep host-ABI calls behind code that only
   `main` reaches.
4. **Eager first-command resolution broke `||`.** `nosuch || echo fallback`
   returned 400. Now resolution is eager only for pure `&&` chains.
5. **`set -e` in demo EXIT traps** turned the killed host's 143 into the
   script's exit status. Fixed in demo-e4 and demo-w1.
6. At -O1 clang turns the demo's recursion into a loop. Stack demos use -O0
   with a 256 MiB linear stack to reach the wasm call-stack limit.

## Remaining issues / not done

- **Pipes are buffered**, not streaming. `yes | head` would never finish
  (the timeout ends it). There are still no variables, loops or `cd` (use
  `go -C dir`).
- **The shared GOCACHE trusts all agents.** Any agent's `go` can write
  cache entries that another workspace's builds will use, and go test
  results are shared too (correct Go semantics). This is fine for one
  trust domain. Separate tenants need a GOCACHE per tenant, or a
  read-only shared std cache plus a private overlay.
- **Cold Go registration takes 3.5-16 min** depending on VM noise; most of
  it is the std warm-up. Shipping a prebuilt GOCACHE seed (or
  precompiled `.cwasm` files) with the toolchain would remove it. A fresh
  host restart with the disk cache populated only reloads (~0.1-0.7 s).
- **Winch is x86-64 only.** On aarch64 hosts the fallback is Cranelift
  everywhere: correct, but slower first runs.
- **Readiness.** For wasip1, ready means "called accept", not "the handler
  works". For wasip2 it is a connect probe, which a one-connection server
  sees as a short empty connection.
- **Tier-up limits.** At most one background compile at a time; requests
  that arrive meanwhile are dropped and retried on the next run. The
  32-entry memory cache can evict a program that is still being iterated
  on, which then gets recompiled.
- **Failed runs.** `exit_code` is still null for traps (state `failed`).
  Runners must check `state`/`trap`.
- **Still slow:** C++ compile time (libc++ headers in an assertions-enabled
  clang), and std packages outside the warm-up set (first use costs tens
  of seconds per heavy package).
