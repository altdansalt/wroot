## Task T5 — develop the wasmdev service using wasmdev itself
The service's own control plane is a Go program (it runs as wasm). Its source is in `./control/` in your working dir
(a snapshot — you can't deploy it; that's fine). Implement this feature in that source and prove it with tests run
**through the service** (`go vet`, `go test`, and `go build` of the control plane, all via the API):

Feature: **streaming pipes in the `cmd` mini-shell.** Today pipes in `cmd` (`a | b`) are buffered: the left side runs to
completion before the right side starts, so `yes | head -n 3`-style pipelines never finish and large intermediate
outputs are held in memory. Make pipelines stream between stages where the underlying execution API allows it, or — if
the host API makes true streaming impossible — find the best design within the control plane, implement it, and explain
precisely what host capability would be needed. Read the code first (look for the shell runner and how runs are executed).
Add unit tests for whatever logic you can test without the host. Deliver: the modified `control/` tree, `PATCH.diff`
against the original snapshot (keep a pristine copy before editing), and the API calls/outputs proving vet/test/build pass.
